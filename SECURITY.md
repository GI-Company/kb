# Security

Kernos runs untrusted-ish code by design: agents write TypeScript that
executes in the user's browser, and users write applets that do the same.
This document states what is actually defended, what is deliberately not,
and where the known holes are. It describes the current build, not an
aspiration — if something here stops being true, the document is wrong and
should be fixed.

Contact for reports: **g.intel.co@outlook.com**. Please don't open a public
issue for anything exploitable.

## Threat model

**In scope**

- Agent-generated code doing something the user didn't ask for
- User-written applet code reaching outside its sandbox
- Server-side request forgery via the terminal's network commands
- Credential exposure (Groq key, Supabase service-role key)
- One user reading another user's data
- Cost/abuse: unmetered use of paid APIs

**Out of scope**

- A malicious *user* attacking their own browser session. Everything the
  sandbox can do, the user could already do in devtools. The sandbox exists
  to bound what an *agent* does on the user's behalf, and to stop a mistake
  from destroying data — not to protect the user from themselves.
- Anything requiring a compromised Groq or Supabase account.

## Boundaries

### Executed code (applets and `kernos.exec`)

`kernos.exec` runs on a **Web Worker**. The timeout ends with
`terminate()`, so synchronous code is genuinely preempted — a
`while (true) {}` is killed rather than hanging the tab. Measured: a 2s
budget terminates at ~2001ms with the main thread still ticking throughout.

The worker holds **no capability references**. It cannot touch the VFS, the
models, the bus, or the network directly; it can only ask the host over
`postMessage`, and `lib/kernosExec.ts` decides whether to answer. Killing
the thread therefore cannot leave a half-applied capability behind.

Enforced per execution:

- Call budgets — `agentAsk` 5, `bnlm` 5, `vfs` 50, `kernelPublish` 20.
  A timeout alone does not bound cost, because in-flight billable calls
  continue after the caller has been handed an error.
- Blocked bus topics — `vm.spawn`, `task.run`, `sys.consolidate`.
- VFS access scoped to the calling user's id.
- No network, no DOM, no raw imports, no React.

Applets (`components/apps/DynamicApplet.tsx`) render in a **closed shadow
root** with the same restricted kernel proxy. They *do* run on the main
thread, because they are UI — so an applet with an infinite loop will still
hang the tab. That is a real, accepted difference: applets are written by
the user in front of them, not generated by a model.

### Network commands (`curl`, `dig`, `ping`, `render`)

Restricted to signed-in accounts (`lib/verifyAuth.ts` validates a Supabase
access token server-side). Guests get the coreutils-only sandbox.

`lib/networkGuard.ts` blocks private, loopback, link-local, and CGNAT
ranges for both IPv4 and IPv6, and re-checks on **every redirect hop**.

> **Known hole: DNS rebinding.** A hostname that resolves to a public
> address at validation time and a private one at connection time is not
> caught. Closing it requires resolve-then-connect-by-IP, which `fetch`
> does not expose. Mitigated only by the signed-in requirement.

### Shell execution (`/api/exec`)

Allowlisted commands, argument sanitization (rejects shell metacharacters,
`..`, absolute paths), a fresh `mkdtemp` jail per invocation, stripped
environment, hard timeout. Each command's existence is checked before
running, so an allowlisted-but-absent binary fails cleanly.

### Secrets

- `GROQ_API_KEY` is read only inside `api/chat.ts` and never returned to a
  client. It cannot leak through normal use, only through project
  misconfiguration.
- `SUPABASE_SERVICE_ROLE_KEY` is server-only and never `VITE_`-prefixed.
  Anything `VITE_`-prefixed is compiled into the browser bundle and must be
  treated as public — the Supabase anon key is safe there by design,
  because RLS is what enforces access.

### Data isolation

Row-level security scopes every table to `auth.uid()`. Enforcement is in
the database, not in application code, so a client-side mistake cannot
widen access. Guests are local-only: their data never leaves the browser.

### Browser headers

`vercel.json` sets COOP/COEP (required for `SharedArrayBuffer`, which BNLM's
parallel training uses), `nosniff`, `Referrer-Policy`, a `Permissions-Policy`
denying camera/mic/geolocation/payment/USB, and a CSP.

> **The CSP allows `'unsafe-eval'`, and cannot not.** In-browser compilation
> *is* the product: both the applet compiler and the exec sandbox construct
> functions from generated source. A CSP forbidding that would disable the
> feature it is meant to protect. Everything else is constrained — no inline
> scripts (the build emits none), `object-src 'none'`, `base-uri 'self'`,
> `frame-ancestors 'none'`, and `connect-src` limited to Supabase and
> PostHog.

## Abuse and cost controls

| Control | Status |
|---|---|
| Guest quota, 15 min/day/IP | Enforced; **fails closed** in production if the service-role key is missing |
| Per-IP rate limiting on `/api/chat`, `/api/exec` | **In-memory, per-instance — not distributed** |
| Per-execution call budgets in `kernos.exec` | Enforced |

> **Known hole: rate limiting is not distributed.** `lib/rateLimit.ts` keeps
> counters in the memory of a single warm function instance, so limits are
> per-instance rather than global. Under concurrency an attacker gets
> roughly (limit x instances). Fixing it needs a shared store — Upstash
> Redis is the standard pairing with Vercel. `lib/rateLimit.ts` is
> deliberately the only place this decision lives, so the fix is a change to
> `checkRateLimit`, not to every call site.

> **Accepted hole: the guest quota fails open on a transient DB error.**
> Someone who can reliably break the database call gets unmetered access.
> The alternative — locking every guest out during a Supabase incident —
> is worse for a free tier whose purpose is frictionless trial. A *missing
> key* in production is treated differently and fails closed, because that
> is a misconfiguration rather than an outage.
